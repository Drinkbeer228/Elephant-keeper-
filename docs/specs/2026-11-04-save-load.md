# Спецификация: Save/Load (сохранение смены)

Дата: 04.11.2026. Согласовано с пользователем: порядок работ — ① Save/Load → ② Звук → ③ ИИ слонов на FSM.
Три обязательных требования пользователя к первому инкременту: `mapId` в корне, `schemaVersion`, round-trip тест с проверкой детерминизма PRNG.

## 0. Цель и принципы

Цель — зафиксировать состояние смены (`State`) в JSON и восстановить его байт-в-байт, чтобы:

- длинные смены и отладку ИИ можно было продолжать с точного момента, а не перезапускать смену;
- будущие изменения схемы (FSM слонов, инвентарь) не приводили к падению при загрузке старых сейвов;
- состояние, сохранённое на одной карте, нельзя было молча восстановить на другой (слон и тюк окажутся в стене).

Принципы:

- **Симуляция не знает про хранилище.** Ядро `sim/save.ts` работает только с данными (сериализация/десериализация + проверки). Запись в `localStorage`, кнопки UI и экспорт файла — слой приложения (`main.ts`, `ui/hud.ts`), инкремент 2.
- **Детерминизм — часть контракта.** В `State` уже лежат `seed` и нативное числовое состояние `rng` (mulberry32, см. `sim/rng.ts`). Сохраняем оба как есть: после загрузки последовательность случайностей продолжается ровно там, где оборвалась.
- **Строгая проверка при загрузке, мягкое поведение в рантайме.** Несовместимый сейв — причина отказа (enum `SaveRejectReason`), никаких исключений с нечитаемым текстом и никакого «починим по ходу».

## 1. Формат сохранения

```ts
interface SaveFile {
  schemaVersion: number; // схема State, стартуем с 1
  mapId: string;         // 'modern' | 'legacy' — идентификатор карты из src/data/map.ts
  floor: { cols: number; rows: number }; // размер сетки на момент записи — вторая линия защиты от смены карты
  savedAt: number;       // unix ms (реальное время, для списка сохранений)
  state: State;          // полное сериализуемое состояние (JSON-safe копия)
}
```

Почему `state` целиком, а не выборка полей: `State` спроектирован как чистые данные
(числа, строки, массивы, плоские объекты) — всё это ложится в JSON без потерь. Выборочная
сериализация создала бы второй источник правды и гарантированно разошлась бы с типами при
первом же добавлении поля. Стоимость — объём (сетка клеток ~12 000 записей × компактный вид);
для localStorage это сотни КБ, допустимо. При разрастании — следующий шаг: gzip через CompressionStream.

### 1.1 Привязка к карте (`mapId`)

В `src/data/map.ts` появляется `export const MAP_ID = useLegacyMap ? 'legacy' : 'modern'`.
Загрузка отказывает с причиной `'wrong-map'`, если `save.mapId !== MAP_ID`. Проверка дополняется
сверкой `floor.cols/rows` с текущей сеткой (`'size-mismatch'`) — на случай, если в будущем две карты
получат один id, но разный размер.

### 1.2 Версионирование схемы (`schemaVersion`)

- Пишем всегда `SCHEMA_VERSION = 1`.
- При загрузке: `version > SCHEMA_VERSION` → `'newer-version'` (сейв из будущей сборки — открывать нечем);
  `version < SCHEMA_VERSION` → ищем миграцию в реестре `migrations: Record<number, (raw) => raw>`;
  отсутствие цепочки → `'old-version'`. Реестр пуст — для v1 миграций нет, сам механизм обязателен,
  чтобы v2 не потребовал переписывать загрузку.
- Перед структурной валидацией идёт минимальная проверка «это вообще наш файл»: наличие
  `schemaVersion`/`mapId`/`state` → иначе `'malformed'`.

### 1.3 Что не входит в сейв

Поля рантайма сцены (камера, пулы спрайтов, HUD) — их в `State` нет по построению. Отдельный
будущий пункт: `held` предмета игрока содержит те же данные, что и элемент `items[]` (ссылка),
в JSON ссылка превращается в копию — десериализация обязан восстановить ссылочную идентичность
(`player.held === items[i]`), иначе `drop()` удалит не тот объект. Это единственное место `State`,
где есть алиасинг (`nested` тазов — вложенные массивы, остаются копиями-внутри-копии, семантика совпадает).

## 2. API модуля `src/sim/save.ts`

```ts
export const SCHEMA_VERSION = 1;
export type MapId = 'modern' | 'legacy';
export type SaveRejectReason =
  | 'malformed'        // не JSON / не объект / нет обязательных полей верхнего уровня
  | 'newer-version'    // schemaVersion больше текущего
  | 'old-version'      // schemaVersion меньше, миграции нет
  | 'wrong-map'        // mapId не совпал с загруженной картой
  | 'size-mismatch'    // размер сетки не совпал
  | 'corrupt-state';   // тело state не проходит структурную проверку

serializeSave(state: State, mapId?: string): string        // запись: JSON + header
deserializeSave(json: string): SaveResult                  // чтение без валида: {ok:true,file}|{ok:false,reason}
loadStateFromSave(json: string, ctx: LoadContext): LoadResult
                                            // полный путь: парсинг → версия → карта → валидация → клон
type LoadResult = { ok: true; state: State } | { ok: false; reason: SaveRejectReason; detail?: string }
isValidSaveFile(v: unknown): v is SaveFile                 // структурная проверка (см. §3)
applyMigrations(file: SaveFile): SaveFile | null           // цепочка миграций по версии
```

`ctx: { mapId: string; cols: number; rows: number }` передаётся извне (game-слой подставляет
`MAP_ID`, `MAP.floor`), ядро не импортирует `data/map` — sim-слой остаётся независимым от выбора карты.

## 3. Валидация структуры (`isValidSaveFile`)

Проверяем то, чем физически нельзя играть без падения скриптов (остальное — ответственность
миграций при изменении схемы):

- корень: объект, `schemaVersion` — конечное число, `mapId` — непустая строка, `savedAt` — число, `state` — объект;
- `state`: `seed`/`rng`/`t`/`nextItemId` — числа; `phase` ∈ {'shift','report'};
- `cells` — прямоугольный массив массивов `{kind ∈ CellKind, since:number}`;
- `elephants` — непустой массив объектов с `id:string`, числами координат, `state` ∈ ElephantState, `tally`;
- `player.held` — `null` или объект с `id/kind/x/y`;
- `partner.mode` ∈ PartnerMode;
- `log` — массив объектов `{kind,text}`.

Дополнительно перед приёмом сейва проверяем отсутствие циклов и `undefined`-значений
(`JSON.stringify` выбрасывает TypeError на циклах — ловим и отдаём `'malformed'`, а не падение).

## 4. Round-trip контракт (тесты)

`tests/save.test.ts`:

1. **Глубокое равенство:** `cleanShift(seed)` → прогон `tick(...)` ~200 шагов с командами →
   `serializeSave` → `loadStateFromSave` → `deepEqual(restored, original)`, плюс отдельная проверка
   `restored.player.held === restored.items.find(i => i.id === heldId)` (восстановление ссылки).
2. **Детерминизм PRNG:** два одинаковых состояния (оригинал и восстановленное) прогоняются
   `advance()` на N минут с одними и теми же командами; сравниваем `rng`-состояние и результат
   `JSON.stringify` обоих — расхождение ровно 0%.
3. **mapId:** сейв с `mapId:'legacy'` отвергается при `ctx.mapId:'modern'` с `'wrong-map'`;
   сверка размеров сетки даёт `'size-mismatch'`.
4. **Версии:** `schemaVersion: 99` → `'newer-version'`; `schemaVersion: 0` без миграции → `'old-version'`;
   мусор/не-JSON → `'malformed'`.
5. **Размер:** JSON сейва полной смены укладывается в лимит localStorage-слота (sanity-тест < 4 МБ).

## 6. Риски

- `Infinity` (`musthNextAt`) сериализуется в `null` — при загрузке восстанавливаем `Number.POSITIVE_INFINITY`
  для этого поля явно (поле означает «нет события»); включено в инкремент 1.
- Объём сетки 120×100 ≈ 12 000 клеток: JSON-строка порядка 0.5–1 МБ. Для localStorage лимит 5 МБ — ок;
  для автосейва каждые 30 с может быть тяжело — в инкременте 2 решим дельта-снимком или debounce.
- Структурная валидация сознательно неполная (не каждый вложенный объект): она защищает от падения,
  а не от логической порчи; за схему отвечает `schemaVersion` + миграции.
