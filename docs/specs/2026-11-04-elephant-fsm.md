# Спецификация: ИИ слонов на FSM с характерами

Дата: 04.11.2026. Пункт ③ мастер-плана (после ① Save/Load и ② Процедурного звука).
Проект: Keeper Sim. Модули: `src/sim/elephants.ts` (логика), `src/data/elephants.ts` (профили),
`src/sim/types.ts` (схема), `src/game/elephantView.ts`, `src/ui/hud.ts` (представление).

## 0. Цель и принципы

Цель — превратить текущий «императивный набор if» в поведении слонов в **честный конечный
автомат состояний (FSM)** с явным деревом переходов, и наложить сверху **систему характеров
(темпераментов)**, которая модифицирует пороги и приоритеты, а не переписывает логику нужд.

Что это даёт:

- **Отлаживаемость.** Состояние + очередь событий перехода можно сохранить сейвом (готовый
  Save/Load) и воспроизвести байт-в-байт (детерминированный Mulberry32 в `State.rng`). Любой баг
  поведения = seed + момент времени, никаких «поймай снова».
- **Расширяемость.** Новые состояния (например, `beg` из этапа стажировки) добавляются как запись
  в реестр состояний + рёбра в таблицу переходов, без правок в других ветках.
- **Наблюдаемость.** Переходы пишутся в `state.log` (события `kind:'ai'`) — игрок и тесты видят,
  *почему* слон поступил именно так. В перспективе — отладочный оверлей «покажи FSM Претти».

Принципы:

- **Логика остаётся в `sim/`**, чистой от Phaser/DOM. Никаких новых полей вне `State`.
- **Нужды (needs) — сенсоры, не состояния.** Голод/жажда/мочевой/кишечник/скука накапливаются в
  `updateOne` ровно как сейчас; FSM только *реагирует* на них через guard-условия переходов.
- **Срочность имеет приоритет над рутиной.** Переходы делятся на классы (`urgency`), и более
  срочное событие может прервать менее срочное состояние (выгнать из `sleep` в `signal` нельзя —
  пузырь ночью копит медленнее; а вот прервать `idle` на `signal` — можно).
- **Характер — данные, а не код.** Temperament — это профиль множителей и допусков, читаемый из
  `data/elephants.ts`. Логика сравнивает числа, не имена («капризный» нигде не встречается в `if`).
- **Обратная совместимость сейвов.** Новые поля слонов — опциональные; `schemaVersion` остаётся 1
  (поле `traits` уже сериализуется целиком, новые поля попадают в тот же объект). Файлы без новых
  полей грузятся и дообираются дефолтами при загрузке (soft-migration значения, не схемы).

## 1. Текущее состояние (что есть сегодня)

`Elephant.state: ElephantState` — плоский union из 14 значений (`types.ts`), но **это не FSM**:
переходы размазаны по `decide()` (~60 строк последовательных `if` со случайными шансами внутри),
`arrive()`, `startSignal()`, `pee()`, плюс спец-ветки в `updateOne` (муст, туалет). Проблемы:

1. Нет явной таблицы «из какого состояния в какой вход и при каком условии» — дерево переходов
   приходится восстанавливать по коду.
2. Приоритеты заданы порядком `if` вперемешку с `chance(state, …)` — характеры некуда повесить.
3. Черты характера есть (`traits.appetite/messiness/aggression`, параметры профиля вроде
   `boredomFactor`, `stereotypy`), но они торчат отдельными магическими числами в разных ветках.
4. Прерывание невозможно: слон в `eatHay` досидит таймер, даже если лопнул мочевой.

## 2. Архитектура FSM

Модуль живёт в `src/sim/ai/`: `types.ts` (контракты), `engine.ts` (`stepElephant`, выбор перехода),
`states.ts` (реестр `Record<ElephantState, AiStateDef>`), `rules.ts` (правила `assess` + темпераменты).
`elephants.ts` оставляет себе физиологию (накопление нужд, `trample`, `wetness`) и делегирует
поведение: вместо `switch (e.state)` вызывается `stepElephant(state, e, p, t, dt, dtReal)`.

### 2.1 Реестр состояний

Каждое состояние — запись `AiStateDef`. Ядро `tick`-цикла не знает имён состояний, только реестр.

```ts
// src/sim/ai/states.ts
export interface AiContext {
  s: State;            // мир (кратко `s`, как в остальной симуляции)
  e: Elephant;         // этот слон
  p: ElephantProfile;  // его профиль
  t: Temperament;      // разрешённый темперамент (профиль × overrides)
  dt: number;          // игровые минуты за шаг
  dtReal: number;      // реальные секунды за шаг
}

export type Guard = (c: AiContext) => boolean;      // условие входа/перехода, чистая
export type Effect = (c: AiContext) => void;         // побочные действия (emit, клетки…)

export interface Transition {
  to: ElephantState;
  when: Guard;               // проверяется каждый тик, пока живёт текущее состояние
  priority: number;          // больше = срочнее; равные — по порядку в массиве
  interrupt?: 'none' | 'finish' | 'now'; // см. 2.3
}

export interface AiStateDef {
  id: ElephantState;
  enter?: Effect;            // один раз при входе (поставить tx/ty, emit, обнулить поле)
  tick?: (c: AiContext) => void; // поведение «внутри», заменяет case'ы switch
  exit?: Effect;
  transitions: Transition[]; // статические рёбра этого узла дерева
  fallback?: ElephantState;  // куда идти, когда timer истёк и ни один when не сработал
                             // (обычно 'assess' — см. 2.4)
}
```

Переход выполняется так: `exit(old) → assign(e.state = to, e.timer …) → enter(new)`.
`enter` сам решает, сколько жить (`e.timer`), чтобы не плодить поля.

**Детерминизм — контракт.** Движок вызывает guards и effects в строго фиксированном порядке:
для текущего состояния — его `transitions[]` по индексам; при истечении `timer` — `fallback`;
затем правила `assess` сверху вниз (§2.4). Никаких `Object.keys` по нерегистрируемым структурам и
никакого `Math.random` — только `sim/rng.ts` поверх `State.rng`. Поэтому прогон после load даёт
байт-в-байт тот же путь FSM, что и непрерывный прогон (тест §6.1).

### 2.2 Дерево состояний (полное)

Группировка узлов — для чтения спеки; в коде это плоский реестр `Record<ElephantState, AiStateDef>`.

**Базовые (физиология, уже есть):**

| id | смысл | таймер/выход |
|----|-------|--------------|
| `assess` | **новый** узел-роспускник: ничего не делает 0–1 мин, запускает выбор цели | всегда уходит в целевое состояние |
| `idle` | стоит, смотрит | 3–8 мин → `assess` |
| `walk` | идёт к `tx/ty` (маршрут через `nav`) | прибытие → `arrive(next)`; цель пропала → `assess` |
| `eatHay` | сено из кормушки | hunger<5 \| кормушка пуста \| 15–30 мин → `assess` |
| `eatBasin` | каша/овощи из своего таза | 12 мин → `finishBasin` → `assess` |
| `drink` | поилка | thirst<5 \| поилка пуста \| 10 мин → `assess` |
| `peeing` | **новый**: акт мочеиспускания (под бак или мимо) — выделяется из мгновенного `pee()` | ~1 мин → `assess` |
| `defecating` | **новый**: присел, куча. Переносит дефекацию из фонового `if (bowel>=100)` в `updateOne` в видимое поведение | ~1 мин → `assess` |
| `sleep` | лежит на подстилке | bedtime→nightEnd; внутри — ночные прерывания |

**Про перенос физиологии в состояния.** Сейчас и моча, и кал — мгновенные побочные эффекты
(`pee()` вызывается прямо из ветки `signal/walkCommand`, куча падает из `if (e.bowel >= 100)`).
FSM требует, чтобы у акта был узел с длительностью: это даёт киперу окно реакции («слон присел —
ещё можно успеть подставить бак») и делает событие наблюдаемым. Поэтому:

- `pee(…)` остаётся функцией-эффектом (её зовут `walkCommand` и тесты), но переход в неё теперь
  через состояние `peeing`: `enter` выбирает бак/мимо, `tick` держит 1 мин, `exit` пишет результат.
- Дефекация: `when bowel >= 100` становится guard'ом перехода в `defecating` (приоритет
  physiological); эффект `dropDung` переезжает из `updateOne` в `enter(defecating)`. Фоновый
  `if` в `updateOne` удаляется — иначе куча появится раньше, чем слон «присядет». Исключение —
  купание в бассейне: там остаётся отдельная ветка (`floats`), потому что слон не выходит из воды.

**Коммуникация с кипером:**

| id | смысл |
|----|-------|
| `signal` | просится в туалет (топот/стойка у решётки); `signalLead` минут → `peeing` |
| `walkCommand` | «давай гуляй» — ведём к баку; `pee` по приходу или по таймауту |
| `beg` | **новый**: тянет хобот к киперу за лакомством (см. §4.3) |

**Досуг и негативное:**

| id | смысл |
|----|-------|
| `sway` | стереотипия, качается (скука ≥ порог && `stereotypy`) |
| `scratch` | чешет бок о дерево |
| `play` | покрышка |
| `bathe` | бассейн |
| `reach` | дотянулся хоботом до предмета за решёткой (шалость) |
| `charge` | **новый**: муст — идёт на цель (игрок/напарник), заменяет current спец-ветку |
| `spooked` | **новый**: испуган (громкий звук/резкое событие), отходит от источника |

Итого 21 узел: **14 существующих имён** (`idle`, `walk`, `eatHay`, `eatBasin`, `drink`, `signal`,
`peeing`, `walkCommand`, `sleep`, `sway`, `reach`, `bathe`, `scratch`, `play`) и **7 новых** —
`assess`, `defecating`, `beg`, `charge`, `spooked`, плюс служебные `arrive`-диспетчер (становится
effect-функцией, а не состоянием) и явный акт мочеиспускания на месте зарезервированного имени.

Важно про `peeing`: оно уже входит в union `ElephantState` (`types.ts:54`) и в список валидаторов
схемы (`save.ts:303`), но **никогда не присваивается** — сейчас мочеиспускание мгновенно внутри
ветки `'signal'`. FSM использует это имя как настоящий узел с длительностью, без переименований и
без расширения схемы сейва.

**Совместимость имён.** `ElephantState` расширяется union'ом только новыми id; старые значения не
переименовываются и не удаляются. Это осознанное решение: представление (`elephantView.ts`
выбирает кадры по `e.state`, `hud.ts` рисует бейджи `sleep/sway/praise`) остаётся нетронутым,
а новые состояния получают визуал инкрементом 5. Сейвы со старыми именами грузятся как есть.

**Разделение `signal`.** Сегодня `'signal'` используется двояко: и как «слон просится» (топот/
стойка у решётки), и как таймер перед мочеиспусканием — ветка `switch` просто ждёт и зовёт `pee()`.
В FSM это два разных узла: `signal` (демонстрация, длится `signalLead`) и `peeing` (сам акт).
Переход `signal → peeing` явный. Для слонов без сигнала (`p.signal === 'none'`) `startSignal()`
раньше сразу звал `pee()`; теперь он входит прямо в `peeing` — семантика та же, но событие видно
на минуту раньше (Одри/Цезарь «рассаживаются» без предупреждения).

### 2.3 Классы срочности и прерывания

```ts
export const URGENCY = {
  physiological: 100, // signal/peeing/defecating — не терпят
  danger: 90,         // charge (муст), spooked
  care: 70,           // walkCommand (ведёт к баку), eatBasin (еда стынет)
  need: 50,           // eatHay/drink/sleep
  leisure: 30,        // play/bathe/scratch/reach/sway
  neutral: 10,        // idle/assess/walk без цели
} as const;
```

Правило вытеснения: активный переход с `priority = P` прерывает текущее состояние,
если `P >= URGENCY[category(current)] + HISTERESIS (10)`. Прерывание щадящее:

- `interrupt: 'now'` — немедленный выход (физиология, опасность);
- `interrupt: 'finish'` — состояние досидит минимум `minCommit` секунд (сон не будим зря,
  `eatBasin` доедает);
- `interrupt: 'none'` — узел никогда не прерывается извне (`peeing`, `walkCommand`:
  слон уже на пути к баку, дергать вредно).

Это заменяет хаос `if` одним вызовом `resolveTransition(c)` раз в тик на слона.

### 2.4 `assess` — единственный планировщик

Все «рутинные» решения принимаются **только** из `assess` (роспускника). Порядок — жёсткий список
правил `(guard, target, weight)`, где `weight` модифицируется темпераментом (§4):

```
1. basin рядом и голоден      → eatBasin     (care)
2. thirst > 60·T.thirstGreed   → drink        (need)
3. hunger > hungryThreshold    → eatHay       (need)   // ночью 70, днём 45, капризный 55
4. bladder ≥ сигнал            → signal       (physiological)
5. bowel ≥ 100                 → defecating   (physiological)
6. bedtime && сухое место      → sleep        (need)
7. boredom ≥ T.playAt          → play/scratch (leisure) // игривый 25, спокойный 55
8. boredom ≥ batheBoredom      → bathe        (leisure)
9. boredom ≥ sway && stereotypy→ sway         (leisure, bad)
10. boredom ≥ reach && предмет → reach        (leisure)
11. иначе                      → idle / walk(случайная точка)
```

Ветка `musthTimer > 0` переезжает в `charge` как `when`-guard с `priority: danger` из любого
состояния кроме `peeing/walkCommand/sleep` (спящего вожака будит только signal).

## 3. Схема данных и сохранение

```ts
// types.ts — добавления (все опциональны, schemaVersion НЕ меняется)
export type TemperamentId = 'capricious' | 'calm' | 'playful' | 'dominant' | 'shy';

export interface Elephant {
  // ...существующие поля...
  fsm?: {
    since: number;          // state.t, когда вошли в текущее состояние
    last: ElephantState;    // откуда пришли (для «zigzag»-детектора и логов)
    transitions: number;    // счётчик переходов за смену — в табель
    committedUntil: number; // до какого t состояние неприкосновенно (minCommit)
  };
  temper?: TemperamentId;   // назначен профилем; undefined = читать из ELEPHANTS
  mood: number;             // 0..100 фоновая эмоция: копится от неухоженности, сбрасывается заботой
  spookLevel: number;       // 0..100 страх; шум/незнакомцы поднимают, еда/кипер рядом гасят
  socialDebt: number;       // минуты без контакта со стадом/кипером — триггер beg
}
```

- `temper`, `mood`, `spookLevel`, `socialDebt` — обычные числа/строки → сериализуются штатно.
- **Валидатор состояния.** `save.ts` держит белый список `ELEPHANT_STATES` (строка 301) и сверяет
  по нему `e.state` при загрузке (`isValidSaveFile`). Новые id (`assess`, `defecating`, `beg`,
  `charge`, `spooked`) **обязательно** добавляются в этот список тем же PR'ом, что и union в
  `types.ts`: иначе живой сейв, снятый на новом состоянии, будет отвергнут как `'corrupt-state'`.
  Тест §6.5 покрывает это напрямую (save→load на каждом из новых состояний).
- `fsm.*` — новый опциональный объект. Добавляем `'fsm'` в `NULLABLE_OPTIONAL_FIELDS`? **Нет**:
  объект отсутствует целиком в старых сейвах, поэтому на загрузке делаем `ensureFsm(e)`
  (добор дефолтов) в `loadStateFromSave` после `restoreUndefinedFields`. Это единственный
  special-case, и он безопасен: старый сейв ≠ новая схема, но поведение от этого не зависит
  (`fsm` нужен только для наблюдаемости и minCommit).
- Значения `Infinity` в новых полях не заводим (sidecar уже есть, но бережём контракт §8 риска).

## 4. Характеры (Temperament)

### 4.1 Модель

Темперамент = вектор множителей над порогами/скоростями накопления + допуски поведения.
Ноль сравнений имён в логике — всё через `t: Temperament`.

```ts
// data/elephants.ts
export interface Temperament {
  id: TemperamentId;
  label: string;              // «капризная» — для текста осмотра
  // накопление нужд (множители к BALANCE.elephant.*)
  boredomRate: number;        // темп скуки
  fearRate: number;           // темп роста spookLevel от раздражителей
  // пороги (абсолютные, модифицируют §2.4)
  playAt: number;             // с какой скуки идёт играть (низкий = игривый)
  reachAt: number;            // с какой скуки ломает предметы
  swayRisk: number;           // вероятность скатиться в стереотипию при boredom≥sway
  eatThresholdDay: number;    // голод, при котором идёт к кормушке днём
  signalPatience: number;     // минут, которые слон «терпит» после сигнала до pee
  // социальные
  begChance: number;          // шанс начать выпрашивать при социальном долге
  followLeader: number;       // 0..1 tendency держаться ближе к вожаку комплекса
  aggressionFloor: number;    // нижняя планка агрессии traits.aggression
  // реакция на кипера
  praiseValue: number;        // множитель эффекта похвалы/лакомства на mood
  trustDecay: number;         // скорость падения доверия при неухоженности
}
```

### 4.2 Пять архетипов и распределение по стаду

| id | label | суть | ключевые числа |
|----|-------|------|----------------|
| `capricious` | капризная | долго не подходит к кормушке, быстро скучает, легко в sway, часто beg | playAt 30, reachAt 50, swayRisk .6, eatThresholdDay 55, patience 3, begChance .5, trustDecay 1.4 |
| `calm` | спокойная | высокий порог скуки, предсказуемый ритм, почти не пугается | playAt 55, reachAt 75, swayRisk .15, patience 12, begChance .1, fearRate .4 |
| `playful` | игривая | low playAt, много bathe/play, ломает игрушки на радостях | playAt 22, reachAt 55, aggressionFloor 1.2, begChance .35 |
| `dominant` | доминантная | не уступает место у кормушки, раньше всех на сигнале, муст тяжелее | followLeader −1 (сама лидер), chargeForce 1.3, eat first-override |
| `shy` | пугливая | высокий fearRate, убегает от шума, отказывается от еды в компании | fearRate 1.8, eatThresholdDay 65, spookRadius 6, begChance .05 |

Полный набор полей (`chargeForce`, `spookRadius`, `thirstGreed` в §2.4) фиксируется в интерфейсе
`Temperament` инкрементом 3 — таблица выше показывает только различающиеся значения; остальные
поля равны нейтральной единице/базовому порогу `NEUTRAL: Temperament`.

Назначение (совпадает с docs/context.md и текущими профилями):

- Претти → `capricious` (беспокойный сон, стереотипия, мгновенная реакция на сигнал);
- Марго → `shy` (мало пьёт, пристально смотрит, длинный lead);
- Одри → `calm` (младшая, ровная, оставляет еду);
- Раджа → `dominant` (вожак);
- Барон → `calm` (тяжеловес, молча стоит у решётки);
- Цезарь → `playful` (вечно в бассейне, задира).

Покрытие все пятью архетипами, каждому слону ровно один, overrides в профиле (`temperOverride?`)
разрешают точечную подстройку без нового архетипа.

### 4.3 Как характер меняет поведение (примеры правил)

- `beg`: из `assess`, если `socialDebt > 20 && chance(t.begChance)` и кипер в радиусе 6 —
  состояние `beg` (тянет хобот). Кипер может дать лакомство из кармана (`pocketTreat` уже есть) —
  `socialDebt = 0`, `mood += praiseValue·k`. Игнор → `beg` длится ≤ 3 мин и переходит в `sway`
  (у `capricious`) или обратно в `assess` (у остальных).
- `spooked`: события из `state.log` с `kind:'bad'` и тегом `loud` (грузовик, крик) поднимают
  `spookLevel` у слонов в радиусе `t.spookRadius`; выше 60 — переход в `spooked` (отойти от
  источника), приоритет `danger`. У `shy` порог ниже, у `calm` — почти недостижим.
- Еда: `dominant` вытесняет немодомых от кормушки (slot-конфликт решается в пользу leader-flag);
  `shy` отказывается есть при двух соседях ближе 2 клеток.

## 8. Риски и решения

- **Регрессия поведения.** Инкремент 2 обязан сохранить семантику текущих тестов; сверяем
  golden-прогон (seed 1, 600 мин, сравнение итоговых needs до округления) до и после рефакторинга.
- **Разрастание реестра.** Правила живут в данных (`transitions: []`), не в `switch` — code review
  видит дерево целиком.
- **Производительность.** 6 слонов × ~20 guard-ов × шаг 0.2 мин — ничтожно; extra аллокации
  исключаем (guards — чистые функции без замыканий в горячем цикле).
- **Звук/сейв-контракты.** Новые `kind:'ai'` события не должны спамить аудиомодуль: фильтруем по
  `aiVerbose` на уровне emit.
